# ADR-0001. Ручное развёртывание TimeCapsule через GitHub и git pull

**Статус:** принято  
**Дата:** 2026-10-29  
**Проект:** TimeCapsule, Amazon EC2 (eu-central-1)  
**Специальность:** Informatică aplicată — вариант A

## Контекст

В рамках лабораторной работы приложение TimeCapsule (PHP + PostgreSQL) развёрнуто на одном экземпляре Amazon EC2. Исходный код хранится в публичном репозитории [cloudstudent-cloud/timecapsule](https://github.com/cloudstudent-cloud/timecapsule). Требуется надёжно переносить изменения с компьютера разработчика на сервер, сохраняя конфигурацию `.env`, пользовательские файлы в `storage/` и данные PostgreSQL.

При первом опыте развёртывания важно, чтобы процесс оставался понятным, не требовал CI/CD-платформы и позволял отменять неудачные изменения через историю Git.

## Решение

Выбран **ручной деплой через `git pull` на сервере** (вариант A по специальности Informatică aplicată).

1. Разработчик редактирует исходники на Windows и выполняет `git add`, `git commit`, `git push` в репозиторий GitHub.
2. Разработчик подключается к EC2 по SSH и выполняет:

   ```bash
   cd /var/www/timecapsule
   git pull --ff-only
   composer install --no-dev --optimize-autoloader
   php bin/init-db.php
   sudo systemctl reload php-fpm
   ```
3. Проверяется открытие приложения и маршрут `/health`.
4. При ошибке выполняется `git revert` **на компьютере разработчика**, затем `git push` и повторный деплой на EC2.

Репозиторий является источником истины для программного кода. Сервер скачивает изменения по HTTPS и не хранит учётные данные для отправки коммитов. Секреты и пользовательские файлы находятся вне контроля версий.

## Рассмотренные альтернативы

| Способ | Достоинства | Недостатки | Вывод |
|---|---|---|---|
| **Копирование файлов через `scp`** | Просто для нескольких статических HTML-файлов | Можно пропустить файлы; сложно установить версию; нет удобного отката | Подходит для задания 5, но не для приложения |
| **`git pull` вручную на EC2** | История версий, простой контроль, минимум инфраструктуры | Зависит от внимательности оператора; возможен короткий период ошибок при обновлении | **Выбран** для этой работы |
| **Скрипт `deploy.sh`** | Одна команда и воспроизводимые шаги; меньше риска пропустить действие | Скрипт нужно поддерживать и проверять; сам по себе не обеспечивает нулевой простой или тестирование | Хорошее следующее улучшение |

## Последствия

**Положительные:**

- Изменения прослеживаются по Git-коммитам; сервер получает код из общего репозитория.
- Изменения можно отменить через `git revert`, не переписывая историю.
- `.env`, база данных и загруженные файлы не должны изменяться обычным `git pull`.
- Способ прост в освоении и полностью соответствует варианту A лабораторной работы.

**Ограничения и риски:**

- Команды выполняются вручную; оператор может допустить ошибку.
- `git pull` обновляет файлы неатомарно: во время обновления посетитель может получить ошибку.
- Если `composer install` завершится неудачно после обновления кода, возможна несовместимость кода и библиотек.
- Маршрут `/health` проверяет доступность своего обработчика и БД, но не гарантирует работоспособность всех страниц — в задании 13 главная страница возвращала HTTP 500 при ответе `/health` со статусом `ok`.
- Все компоненты, БД и пользовательские файлы находятся на одном EC2: это единая точка отказа; необходимо резервное копирование.
- В учебной конфигурации используется HTTP без TLS; для реальной эксплуатации нужен HTTPS.

## Последующие улучшения

Добавить автоматические тесты, скрипт деплоя, резервное копирование БД и файлов, HTTPS и атомарное обновление с возможностью быстрого отката.
